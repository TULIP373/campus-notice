# 开发流程

这份流程解决一个具体问题：让同一个 AI 既写代码、又写测试、又判自己通过，它会给自己定一条最容易过的线。
所以顺序是先定合格线、再写测试、再实现，并且写实现的和判通过的不是同一个上下文。

主 Agent 负责方向、拆分、整合和最终判断；子代理只做边界清楚、结果可检查的小任务。角色定义见 `docs/roles/`。

## 步骤

**第 0 步 恢复现场。** 读 `docs/PROGRESS.md` 和其中的“短规则”；没有记录就从第 1 步开始。有记录时不要直接照着“下一步”做，中断可能发生在代码已改、进度还没更新的时候。先核实三件事，再决定从哪接着做：

- 工作区实际改了什么（未提交的修改、未跟踪的文件），和进度记录对不对得上。
- 最近一次有效验证是针对哪个提交的，此后代码有没有再变。
- 项目现在能不能启动，跑一个最小的启动或冒烟检查；顺便确认没有上次留下的进程还在运行。

记录和现状不一致时，以现状为准，并先把 `docs/PROGRESS.md` 改对。

**第 1 步 读合格线。** 读 `spec/main.md` 和 `docs/acceptance.md`。运行 `tools/harness-check.ps1 -Stage ready`，不通过说明规格或验收标准还没填完，先回报用户，不要自己补。

**第 2 步 写测试。** 交给 `test-author`：依据 `docs/acceptance.md` 写出 `docs/test-cases.md`，每条用例标明覆盖哪些 AC 编号。预期行为只来自规格和验收标准，不依据实现来放宽；公开接口、测试框架和已有的测试设施可以读。

**第 3 步 核对覆盖。** 交给 `coverage-checker`：列出“AC 编号 ↔ 测试”对照表，找出没有测试管的编号和假覆盖。然后运行 `tools/harness-check.ps1 -Stage coverage`。有缺口就回到第 2 步，补齐后才往下走。

**第 4 步 搭观测手段。** 先把测试依赖的东西做出来：状态快照、调试入口、固定种子、截图或录帧、日志。没有这些，后面只能靠“代码看起来合理”来判断，那不算验证。

**第 5 步 实现。** 按里程碑推进，先打通主流程再补其余部分。交给 `builder`，每次只给一个范围清楚的小块。实现者不修改验收标准和测试口径。

**第 6 步 提交并运行测试。** 先把实现、测试和配置提交，再针对这个提交跑全部相关测试，把输出存到 `reports/<日期>/`。不通过就：在 `docs/PROGRESS.md` 的“踩坑记录”记一条，修复，重新执行第 6 步。

对关键的新增逻辑和缺陷修复，要留一份证据证明测试抓得住目标错误：实现之前或修复之前测试失败的输出，或者临时引入一个已知错误后测试失败的输出，都可以。失败必须来自目标断言，依赖没装、语法错误、程序没启动造成的失败不算。给本来就正确的功能补回归测试，第一次就通过是正常的，不需要这份证明。

**第 7 步 视觉复核（有界面改动时）。** 交给 `visual-reviewer`：拿真实运行截图对照参考图，只读。不通过就修复后回到第 6 步。

**第 8 步 综合验收。** 交给 `reviewer`：全新上下文、只读、默认不通过。给它规格、验收标准、代码改动和证据，不要给实现者“已经完成”的总结。先逐条核对验收标准，过了再看代码质量。不通过就修复后回到第 6 步。

把验收者返回的结论原样存成 `docs/review-record.md`（格式见下），不改写、不删减它列出的问题。这个文件只保留最近一次复核，更早的移到 `reports/`。

**第 9 步 主 Agent 复核并出报告。** 不照搬子代理的结论：自己看关键改动，重跑必要的验证，然后写 `docs/acceptance-report.md`（格式见下），最后运行 `tools/harness-check.ps1 -Stage final`。

完成需要三样同时成立：测试真实跑过并留下证据、独立复核通过、检查脚本通过。脚本只核对材料是否齐全一致：它查不出测试有没有真的断言、证据内容对不对、复核是不是真的独立，所以它通过不等于质量合格，只是不通过一定没做完。

## 验收报告格式

`docs/acceptance-report.md` 开头写明验证针对的提交，然后每条 AC 恰好一行，结果只用三个词：`PASS`、`FAIL`、`UNVERIFIED`。证据列用反引号写仓库内的文件路径，必须是非空的文件，不能是目录。重新验证后直接改原来那一行，不要追加新行。

```markdown
Verified-Commit: 3f2a9c1

| AC | 结果 | 证据 | 说明 |
| --- | --- | --- | --- |
| AC-RUN-01 | PASS | `reports/2026-01-01/run.log` | 启动无报错 |
| AC-UI-01 | FAIL | `reports/2026-01-01/hud.png` | 血条偏出边框 |
| AC-OBS-03 | UNVERIFIED |  | 还没做固定种子 |
```

没验证就写 `UNVERIFIED`，不要写成 `PASS`。有 `FAIL` 或 `UNVERIFIED` 就回到第 5 或第 6 步继续。

## 复核记录格式

`docs/review-record.md` 开头两行固定，后面是验收者返回的原文：

```markdown
Reviewed-Commit: 3f2a9c1
Verdict: PASS

（验收者的原始结论：逐条核对结果、发现的问题、未解决的事项）
```

`Verdict` 只用 `PASS` 或 `FAIL`。检查脚本核对的是这份记录存在、结论是通过、复核的提交和报告验证的提交一致。它证明不了复核者是否独立、是否看过真实证据，这要靠派活时确实用了独立的验收角色。

## 证据和代码版本

证据只对产生它的那份代码有效。约定如下：

- 实现、测试和配置先提交，验证和复核都针对这个提交，提交号写进报告和复核记录。
- 此后这些文件只要有变化（包括没提交的修改和新增的文件），之前的验证就失效：提交，重跑受影响的 AC，重新复核，更新两处提交号。
- 不算变化的只有验收产物：`reports/` 下的文件、`docs/acceptance-report.md`、`docs/review-record.md`、`docs/PROGRESS.md`。
- 项目不是 git 仓库时，脚本做不了这项检查，会明确提示“未做版本绑定检查”。这种情况下在报告里写明验证的时间和对象，并尽量把项目建成 git 仓库。

## 验收标准或测试有问题时

不允许的是为了让实现过关而降低标准。标准本身可以被修订，但要走明路：

- **用户提出新需求或改需求**：更新规格和验收标准，在 `docs/acceptance.md` 的“修订记录”里记一条。新条目用新编号，不复用旧编号。受影响的 AC 在报告里改回 `UNVERIFIED`，对应的旧证据不再有效。
- **执行中发现标准有错、互相矛盾或无法验证**：你不能自己改。在 `docs/PROGRESS.md` 的“卡点”写清是哪条、矛盾在哪、你建议怎么改；这条 AC 在报告里记 `UNVERIFIED`；继续做不受它影响的部分。两种理解里有一种明显更符合规格时，按那种继续并记入“决定记录”。
- **测试本身写错了**：交回 `test-author` 修改，不由实现者改。改后的预期仍以验收标准为准，在“决定记录”里记下改了什么、为什么。

## 贯穿全程的规则

- **自己拿主意。** 规格没覆盖的实现细节，选最符合目标的做法，记进 `docs/PROGRESS.md` 的“决定记录”后继续。只有 `AGENTS.md`“约束”里列出的情况才暂停，暂停时继续做不依赖它的部分。
- **记进度。** 每完成一步或一个里程碑就更新 `docs/PROGRESS.md`。上下文会被压缩，没写进文件的东西等于没发生。
- **记踩坑。** 解决过的问题记一条：现象、原因、修法、下次规则。容易复发的提炼成一句放进“短规则”。只记真实发生并解决了的。
- **别原地打转。** 同一个失败反复出现且没有新线索时，不要原样重试；换做法，或转去做不依赖它的部分。确实推不动就写清卡在哪、试过什么、需要用户给什么。
- **验证真实运行的东西。** 涉及界面、动画、声音的条目，必须启动真实程序取证。
- **小步提交。** 每个里程碑提交一次，只提交本次相关的文件。
- **如实收尾。** 预算或上下文将要耗尽时，更新进度并交接，报告里写未完成，不要写完成。

## 什么时候可以简化

流程里的每一环都是因为某种失败才加上的。任务很小（一两个文件、半小时内）时，可以省掉子代理分工，由主 Agent 顺序完成，但保留这个顺序：先看验收标准，再写测试，再实现，最后逐条对照出报告。省掉了哪一环，在 `docs/PROGRESS.md` 里写一句。
