# 角色与派活规则

五个固定角色，各有一份职责说明。`.codex/agents/` 和 `.claude/agents/` 里的角色文件只负责设定权限并指向这里，职责内容只在这个目录维护一份。

| 角色 | 做什么 | 能改文件吗 |
| --- | --- | --- |
| [test-author](./test-author.md) | 把验收标准翻译成测试用例 | 只能改测试相关文件 |
| [coverage-checker](./coverage-checker.md) | 核对每条验收标准是否都有测试在管 | 只读 |
| [builder](./builder.md) | 按指定范围写实现 | 只能改主 Agent 允许的范围 |
| [visual-reviewer](./visual-reviewer.md) | 拿真实截图对照参考图 | 只读 |
| [reviewer](./reviewer.md) | 逐条核对验收标准，再看代码质量 | 只读 |

分工要三样同时成立才有用：审查者是全新上下文、立场是挑错、标准是事先写好的。只开两个 agent 却让审查者临场决定什么算合格，等于没分。
同一轮任务里，写实现的不能担任 `visual-reviewer` 或 `reviewer`。

没有子代理的工具里，把角色文件当作一份任务说明：另开一个新会话，让它先读对应的角色文件再干活。

## 派活时必须给的输入

主 Agent 每次派活都要写明，不要让子代理猜：

- 规格路径和验收标准路径。
- 本次负责的 AC 编号或范围。
- 测试用例或测试入口的路径。
- 可以读哪些文件、可以改哪些文件、不能改哪些文件。
- 完成后要返回什么。

任何角色发现这些输入缺失时，直接回报“缺少必要输入”并列出缺什么，不要自己猜路径或版本。

任务要小、清楚、可检查。可以派的例子：

```markdown
任务：实现 AC-LOGIN-01 到 AC-LOGIN-04 的登录表单。
依据：spec/main.md、spec/behavior.md 第 2 节；验收标准 docs/acceptance.md；测试 docs/test-cases.md 的 TC-LOGIN 部分。
范围：可以改 src/auth/ 和 src/pages/login.*；不要改 docs/acceptance.md、docs/test-cases.md 和其他模块。
返回：改了哪些文件、怎么运行验证、覆盖了哪些 AC、还有什么风险或没验证的点。
```

不要派这样的任务：“把整个功能做完”“检查一下有没有问题”“根据规格全部实现”。范围太大，子代理容易跑偏，结果也没法检查。

## 返回格式

完成时返回：

- 做了什么。
- 改了哪些文件。
- 怎么验证的，证据在哪。
- 对应哪些 AC 编号。
- 还有哪些风险、没验证的点或需要主 Agent 决定的问题。

没完成时返回：卡在哪、已经查过什么、需要主 Agent 补什么。

## 并行规则

可以并行：都是只读调查；或各自改的文件互不重叠，且各有独立的验证方式。

不要并行：会改同一个文件；一个任务的结果决定另一个怎么做；几个问题可能出自同一个原因，需要先统一分析。

并行结束后，主 Agent 统一检查改动，确认没有互相覆盖或重复实现。

## 主 Agent 的复核

不能只转述子代理的结论。至少要：

- 检查它有没有超出范围、改了不该改的文件。
- 看关键改动，确认没有顺手重构无关内容。
- 重跑相关测试或检查，而不是只看它贴的输出。
- 先确认验收标准通过，再进入代码质量的讨论。

## 所有角色共同遵守

- 不修改 `docs/acceptance.md`，不降低验收标准或测试要求。
- 不跨版本混用规格、验收标准和测试用例。
- 说“通过”必须附证据；拿不准就按“未通过”报。
